# ADR-001 — Helper protocol (CP4)

**Status:** Proposed — revised 2026-10-15; pending independent CP0 review. This revision does not authorize implementation or open any network surface.
**Spec:** V2 §4.1 (B1, B2), gate 3. **Invariants:** 1 (LAN-only), 2 (originals untouched).

## Context
Photos live on several family computers. The server has to find and pull them without the helper ever changing anything on that machine, and without opening a door any other LAN device could use.

## Decision
1. **Shape.** A small, single-purpose daemon for Linux (systemd user unit) and Windows (a scheduled task at logon, running as the user). It runs in the user's session so it only ever sees what that user can see.
2. **Discovery.** It advertises `_constellation-helper._tcp` over mDNS. The TXT record carries only a random `helper_id` and a protocol version. It never carries a hostname, user name or folder list.
3. **Pairing.**
   - At first run, the helper generates a uniformly random six-decimal-digit code with the operating system CSPRNG. It displays the code only in the local helper UI; the code is never written to logs, telemetry, command-line arguments, or a reusable verifier file.
   - A pairing attempt expires after 2 minutes and is single-use, whether it succeeds or fails. The adult enters the code in the server wizard and confirms the peer identity on the helper itself. Discovery data is only a locator; an mDNS response, helper ID, IP address, or successful TCP connection is never evidence of identity or consent.
   - Pairing uses SPAKE2 as the only code-authenticated key exchange. The proposed interoperable suite is RFC 9382 `SPAKE2-P256-SHA256-HKDF-HMAC`: P-256, uncompressed SEC1 point encoding, SHA-256 transcript hash, HKDF-SHA256, and HMAC-SHA256 confirmation. Use the RFC 9382 §3.3 transcript encoding and §4 key schedule/role-specific confirmation tags exactly; append no ad-hoc fields to that SPAKE2 transcript. Bind application context (protocol version, helper ID, both fresh nonces, roles, and both certificate public-key SHA-256 fingerprints) as RFC 9382 associated data, with canonical length-prefixed encoding and the suite identifier, so both peers authenticate identical context. CP0 must still select, pin, and independently validate an exact maintained implementation/version and test-vector results before approval or implementation; no custom PAKE, unreviewed adapter, unauthenticated key exchange, or plain code comparison is allowed. Until that implementation gate is met, the suite is a proposed wire contract, not an implementation decision. Any mismatch aborts and erases ephemeral secrets.
   - The helper allows at most 5 failed code attempts per pairing window. On the fifth failure, the code is invalidated and pairing is locked for 15 minutes; the lockout survives process restart. A new code is generated only by a local adult action after the lockout. The server also applies a per-helper attempt limit. The PAKE exchange must not expose a reusable offline-verifiable code oracle; the short code is never accepted as a normal password or as a TLS credential.
   - Each side creates a distinct self-signed TLS certificate and pins the peer certificate fingerprint only after successful PAKE and transcript confirmation. All API connections require TLS 1.3 mutual authentication, exact pinned-certificate matching, and the paired helper identity. TLS 1.2 and weaker versions are rejected. Pins are scoped to one helper/server pair; there is no trust-on-first-use or certificate-authority-wide trust.
   - The listener binds only to an adult-selected, up, non-loopback LAN interface and its directly connected prefix; it never binds to wildcard or public interfaces. Each eligible interface/family is shown separately for explicit local selection; no automatic multi-interface binding or public/VPN/tunnel interface is permitted. The accepted peer must be on the selected directly connected prefix, but an IP address, local-subnet result, or firewall match is only an exposure filter—not peer identity. A DHCP address/prefix change, interface replacement, or route/prefix ambiguity closes listeners and active streams until local adult confirmation reselects the interface/prefix. IPv4 and IPv6 are evaluated independently; a missing/failed firewall rule fails closed. mDNS is untrusted discovery only and is not required for manually entered, locally confirmed pairing.
   - The server stores helper pins and the helper stores server pins in per-user, owner-readable-only files (POSIX mode 0600, or equivalent user-only ACL on Windows). Private keys are non-exportable where supported; otherwise they are owner-only and excluded from all logs/backups. No global or shared household credential is used.
   - Re-pairing, certificate rotation, local unpair, or consent revocation invalidates the affected pin/session. A failed request, bad PAKE proof, absent/untrusted certificate, or certificate that does not match the stored pin is rejected and rate-limited; it closes only that connection and never deletes/revokes a stored pin, so unauthenticated traffic cannot force re-pairing. A validly pinned peer presenting a protocol/identity mismatch is refused and audited without file/path data; pin replacement/removal requires explicit local adult action. Revocation is effective immediately: the helper closes active TLS sessions and streams, rejects subsequent requests, removes the paired pin, and requires fresh locally confirmed pairing. The server likewise invalidates its session and pin. Failure to persist or confirm local revocation fails closed; process restart must not resurrect a revoked session.
4. **Consent.** The adult selects folders on the helper machine. The helper stores an explicit allowlist of canonical root identifiers and the consent record locally. The server can request only listed roots; it cannot add roots remotely. Revocation is local, immediate, and atomically closes active streams and invalidates the paired session as described above. Consent changes require a fresh local confirmation and are audited without recording file names or personal paths.
5. **API: read-only by construction.**
   - `GET /v1/folders` returns opaque identifiers for consented roots, with bounded counts and total size; it never discloses absolute local paths.
   - `GET /v1/list?root=<id>&cursor=` returns bounded pages of relative paths, size, and modification/version metadata; it does not assert a content hash for bytes not yet read. The first page creates a server-side, opaque 15-minute snapshot ID and cursor bound to the helper, root handle identity, consent generation, and a bounded manifest of entry names, types, stable file IDs, sizes, and available change/version metadata. Every page re-enumerates and compares the root identity and manifest; any difference, expiry, or inability to complete the comparison invalidates the snapshot and requires a fresh listing. Snapshots are capped by entry count, manifest bytes, and scan time; exceeding a cap returns a retryable refusal, never a partial snapshot presented as complete.
   - Root identity is captured from a held directory handle, not a pathname: POSIX records device+inode and mount identity where available; Windows records volume identity+file ID and the held handle's final path. Root replacement, directory replacement, mount-point crossing/replacement, volume change, or consent-generation change invalidates the snapshot. Resolve beneath the held root without following links; reject any resolution whose final handle/path or volume is not beneath/on the originally consented root/volume.
   - `GET /v1/file?root=<id>&path=` streams bytes for an authorized regular file. It supports bounded `Range` requests for resume, but revalidates the certificate, consent generation, root identity, path, file identity, and authorization on every request and every range. Immediately before opening and before each stream chunk, compare the current consent generation and held-root identity; a concurrent consent change closes the stream before more bytes are sent. The SHA-256 is computed over the exact bytes streamed and returned as the transfer digest; the importer verifies it. Before and after a stream, compare stable file ID, volume/device, size, and available change/version metadata; on any change, terminate with stale-source and do not report successful completion.
6. **Server side.** The import engine is a separate CP4 component and is not approved by this protocol ADR. It must record a per-file cursor and verified hash, survive reboot without duplicate imports, and treat a stale cursor/source as a rescan rather than trusting stale metadata. It may not broaden helper consent or alter originals. Import-engine network exposure and implementation require the CP1-before-network gate plus a separate exact-tree review and acceptance.

## Required security evidence before CP0 approval
- The proposed crypto wire contract is RFC 9382 `SPAKE2-P256-SHA256-HKDF-HMAC`, uncompressed SEC1 point encoding, RFC transcript/key schedule/key-confirmation rules, and canonical application context in RFC 9382 AAD. Before CP0 approval, independently vet and pin the exact maintained implementation, version, dependencies and integrity hashes; verify every RFC 9382 Appendix B test vector and no code oracle/fallback. This repository currently makes no claim that a candidate implementation is vetted.
- Tests prove code expiry, single-use behavior, attempt limit, persistent lockout, wrong/replayed transcript rejection, identity/certificate mismatch rejection, and resistance to mDNS spoofing as an authentication bypass.
- Tests prove unpaired, expired, locally unpaired, consent-revoked, and certificate-revoked peers cannot make or continue API requests; active streams stop on revocation. Invalid requests/certificates must not revoke a stored pin.
- Tests cover explicit interface selection, dual-stack and multi-interface cases, DHCP/prefix changes, firewall failure, non-local peer rejection, TLS version and client-certificate matrix, every method/path, request/resource limits, malformed and encoded paths, symlink/reparse and rename races, root-directory replacement, mount/volume replacement, consent-generation changes during open/stream, Windows held-handle final-path/volume checks, hard-link rejection, Range boundaries, snapshot expiry/change/cap handling, stale cursors, source mutation during hash/stream, and unchanged source checksums.
- The exact test inventory includes positive controls proving valid paired/consented access still works. No test may be weakened, skipped, or replaced with a mock-only assertion to claim acceptance.

## References
- [RFC 9382 — SPAKE2, a Password-Authenticated Key Exchange](https://www.rfc-editor.org/rfc/rfc9382.html), especially §§3.3–4, 6 and Appendix B.

## Consequences
- Tests have to prove the helper cannot write, rename or delete anything (checksums before and after, over the full API surface with fuzzed paths).
- Tests have to prove an unpaired client is refused at the TLS layer and that revoked or expired peers cannot retain access.
- LAN-only is enforced by binding, firewall policy, peer checks, and TLS; mDNS discovery alone never grants trust.
- One more small binary to package on each OS, reusing the CP2 packaging.
- This ADR remains Proposed until its implementation choices and CP0 evidence are independently reviewed against the canonical blob. It does not authorize CP4 coding, CP1 advancement, a release, or deployment.

## Rejected
- **SMB/NFS shares:** needs admin setup on every machine, and it's read/write by default.
- **Pushing from a sync client on each PC:** more moving parts, and it breaks "consent once, on that machine".
